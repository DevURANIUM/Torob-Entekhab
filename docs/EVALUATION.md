# Evaluation methodology

## What runs

`npm run evaluate` runs 33 hand-authored cases through deterministic extraction and the actual search pipeline. `/lab` does the same using database records on every request, displaying its timestamp and mode. The CLI uses the checked-in seed catalog; a modified database can therefore differ. No displayed metric is a static benchmark number.

The benchmark includes Persian/Arabic/English numerals, Arabic letter variants, ranges, decimal millions, brand exclusions, recipients, usage categories, RAM/storage/weight/support constraints, empty results and ambiguous language. Fifteen-plus shopping patterns are supported; this is not a comprehensive Persian corpus. Fixtures overlap the supported parser rules and should be viewed as development tests, not a held-out generalization set.

## Intent metrics

Each case declares only fields it independently expects. Each asserted top-level field contributes one binary result. Nested constraints compare required key/value pairs; expected use-case/brand arrays require the listed values. Overall intent accuracy is passed asserted fields divided by all asserted fields. Cases with no assertions do not inflate this denominator. Budget/brand/use-case/constraint cards use their respective asserted-field denominators.

Subset assertions intentionally tolerate additional fields. This means incorrect extra extraction can escape this metric; future precision/recall or exact-match labels should address it. The visible written-number case expects 25,000,000 Toman, fails, and is retained as a known gap. Ambiguous cases carry explanatory notes even when no field assertion fails.

## Retrieval and ranking

Three cases have independent, manually assigned family-level grades: 3 strong, 2 relevant. These labels are never generated by the ranking function. They cover parent/battery use, gaming and photography. Other cases do not participate in ranking averages. The impossible-iPhone case has an explicitly empty relevance map and is checked by functional tests, not a vacuous recall score.

`Recall@5 = relevant labeled families in the first five / all labeled relevant families`.

`DCG@3 = Σ (2^grade - 1) / log2(position + 1)`, with positions starting at one. `NDCG@3 = DCG / ideal DCG`. The ideal order sorts manually assigned grades. Unjudged returned families receive grade zero within these labeled queries. This may under-credit valid alternatives: labels are incomplete, and we say so.

Top-three relevance is the fraction of the three slots containing positively judged families. Fewer than three returns leave missing slots at zero. Families are deduplicated before metrics, matching the customer shortlist.

## Latency and cost

Offline P50/P95 are nearest-rank-style array percentiles of individual query durations, measured with `performance.now()`. They include normalization, parsing, filtering, scoring, deduplication and clarification probing. They exclude SQLite, network, HTTP handlers, rendering and AI. They are single-process measurements with only 33 samples; do not compare them to production end-to-end latency.

The API also records actual request processing latency from extraction through retrieval/ranking, mode, fallback and model-reported token usage. It does not store query text. The lab summarizes up to 100 recent requests separately from offline timings. AI cost = `(inputTokens * configuredInputRate + outputTokens * configuredOutputRate) / 1,000,000`. Missing or zero configured rates produce unknown cost for successful AI calls, never a fabricated zero. Mock calls cost zero. Failed API requests may have provider-side charges that cannot be known from failed responses.

## Known failures

- Written-out numbers such as «بیست و پنج میلیون» are not parsed by the mock engine.
- “خفن” is ambiguous; the clarification engine may suggest a dimension, but cannot infer a reliable interpretation.
- Unsupported/nonsensical text is not used to fabricate product intent; the UI asks for a useful need and shows no shortlist.
- Complex negation, multiple brands joined by alternatives and brand preference versus requirement remain limited.
- Synthetic support years, scores and prices cannot measure real-world utility.
- Confidence has not been calibrated against user decisions.

## Verification layers

Vitest checks normalization, merge preservation, explicit exclusions, hard filtering, impossible constraints, zero-record behavior, deterministic ranking, weight normalization, audited contributions, confidence/clarification, upgrade deltas and AI error/schema fallbacks. Playwright executes the customer journey, comparison, back navigation, details, selection, debugger, empty-state recovery and overflow checks at 375/768/1440 widths. Browser error listeners reject uncaught runtime errors in the main journey. Screenshot review complements assertions.

Live model accuracy is **not** claimed: no paid API call was used in local verification. The debugger uses the configured provider, but the offline lab always labels its mock mode. No load testing or cross-browser certification is claimed.

## Next evaluation steps

Create a held-out, multi-author Persian corpus; label exact desired intent, disallowed extras, family-level relevance, acceptable constraint relaxation and whether clarification is warranted. Include new product families, mixed numerals, adversarial instructions and spelling variation. Report confidence intervals, per-slice results, disagreement between judges and learning-to-rank baselines. Validate factual data independently of language/ranking tests. Measure user outcome quality before expanding scope.
